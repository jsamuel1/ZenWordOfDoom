# v0.3 "Roast Fixes" — Design

**Date:** 2026-07-02
**Status:** Approved design (from the 2026-07-02 three-reviewer roast: game-design, code-quality, architecture)
**Branch:** `feat/v0.3-roast-fixes` (worktree, based on `main` @ 8533ae8)
**Coordination:** `feat/v0.2-store` is being implemented in a parallel session and moves
`SaveState` into GameCore with monetization fields. **Economy changes are therefore
spec'd here but implementation is deferred** until that branch merges (§10).
This branch keeps `GameStore`/`SaveState` edits minimal to reduce merge conflicts.

## Problem

The roast review found the game's central promise — a creature slowly surfacing as you
solve — broken three independent ways, one real lifecycle bug, a consequence-free Doom
Mode, no day-3 retention hook, and a set of architectural barnacles (two zombie
packages, three hash implementations, docs describing a phantom system, zero app-target
tests). This design fixes all of it except the economy retune (deferred, §10) and the
explicitly out-of-scope items (§12).

## 1. Reveal curve (GameCore)

Stir is currently additive (+0.08/slot, +0.02/bonus, +0.01/hint), so a full 8-slot grid
peaks at 0.56 and a typical grid at 0.24–0.40 before `isComplete` snaps it to 1.0 —
while `SceneRevealView` maps creature visibility to `smoothstep(0.15, 0.85, stir)`.
The reveal is a jump cut.

**New model:** stir is *derived from completion fraction*, not accumulated:

- `progressStir = 0.85 × completionFraction`
  - `.crossword`: `completionFraction = solvedSlotIDs.count / level.slots.count`
  - `.pangramHunt` (boss, no slots): fraction of the level's completion requirement
    met (pangram found counts as the dominant share; remaining words fill the rest),
    using whatever completion rule the engine already consults for `isComplete`.
- Small additive extras remain on top: `+0.02` per bonus word, `+0.01` per hint reveal,
  **capped so pre-completion stir never exceeds 0.95**.
- Completion sets `stir = 1.0` (unchanged).
- Stir stays monotonic — recomputation never lowers a previously reached value.

The engine keeps the same public `stir` property; only its derivation changes.
Tests assert: half-solved grid ≈ 0.42 stir, full-but-one grid ≥ 0.7, monotonicity,
cap at 0.95, boss progression, complete → 1.0.

## 2. Un-block the payoff (app)

Two changes in `GameContainerView`/`GamePlayView` + one in `SceneRevealView`:

1. **Held reveal beat, uncovered.** On `isComplete`: fade out HUD, tray, ribbon, and
   wheel; let the reveal play full-screen for the held beat (2.2 s, 0.8 s with reduce
   motion). **`LevelClearView` appears only after the beat**, then its Continue leads
   to the cut scene as today. The score popup no longer covers the creature.
2. **Lifecycle-safe scheduling.** The `DispatchQueue.main.asyncAfter` chain that pushes
   the cut scene is replaced with a `.task(id: model.isComplete)` + `try await
   Task.sleep` sequence, so backing out of the screen auto-cancels the pending
   navigation push (fixes the confirmed nav-race bug at `GameContainerView.swift:165-177`).
3. **Generated art in the reveal.** `SceneRevealView` routes its scene/creature imagery
   through `GeneratedImageView`'s existing chain (Image Playground cache → bundled →
   procedural) instead of reading only `BundledVisuals`. The on-device art pipeline
   finally shows up during play, with identical fallbacks for CI/simulator.

`CutSceneView.begin()`/`popOut()` gets the same treatment as (2): its three chained
`asyncAfter` calls become one task-driven timeline cancelled on disappear (stops the
stray pop-out audio sting after the player leaves).

## 3. Doom Mode consequences (user-decided design)

At timer expiry, the level's points are **voided** — no retry (the player already knows
the words), no lockout:

- `GameEngine` gains `scoreVoided` state and a `voidScore()` transition, legal only in
  `.doom` mode (the mode field is finally read by the rules). Voiding zeroes `score`
  and all subsequent submissions award 0 points; slots still fill, words still count,
  stir still rises, the level can still be cleared.
- UI at 0:00: scene dims (respecting Reduced Doom — dim less), input pauses, overlay:
  *“The doom has claimed this hour. Continue without points.”* One button: Continue.
  Play resumes with the HUD score shown as a voided `—`.
- A voided clear still unlocks the next level, records the bestiary creature, and
  advances the streak — but records **no best score** and (once the economy lands)
  **no serenity**.
- Settings copy updated to describe the real consequence.

## 4. Daily puzzle + streak surfacing

**Daily puzzle** (SPEC §8 finally shipped) — nearly free given deterministic procgen:

- `LevelGen.DailyPuzzle.seed(for: Date, calendar: Calendar) -> LevelSeed`: FNV-1a over
  `"daily-yyyy-MM-dd"` (user's calendar day) picks theme (hash parity), band (rotating
  medium/hard/expert), and index — same puzzle for everyone on a given day, stable
  across devices (FNV-1a, *not* `String.hashValue`).
- Level id `"daily-2026-07-02"`; `LevelService` recognizes the `daily-` prefix and
  generates via `DailyPuzzle`. Progress records under that id in the existing map.
  After the clear + reveal + cut scene, navigation pops to the menu (no `nextID`).
- `MenuView` gets a **Today's Doom** card: today's state (unplayed / cleared ✓) and
  the streak flame.

**Streak becomes clear-gated and visible:**

- `recordDailyPlay` moves from level `onAppear` (load-and-quit currently keeps a
  streak alive) to `completeLevel` — clearing **any** level counts, daily included.
- The flame + count move onto `MenuView`; Stats keeps the detailed view.

## 5. Level pipeline: honest errors, no double generation

- `ProceduralGenerator`/`WheelPicker` `precondition`s become thrown `LevelGenError`s.
- `LevelService.level(id:)` returns a real failure instead of the `SampleLevel`
  hammock (whose `"garden-001"` id strands the player and writes progress under a key
  nothing reads). `GameContainerView` shows a retry state: *“Couldn't compose this
  level”* + Retry. `SampleLevel` remains for previews only.
- `LevelService` memoizes `[String: Level]` (it's already `@MainActor`).
- The cut-scene route carries `sceneID`/`creatureID` (the finished `GamePlayView`
  already holds them), so `CutSceneContainerView` stops re-running full generation —
  and its FM 20-second budget — to read two strings.

## 6. One hash, honest names, small UX wins

- Single `fnv1a(String) -> UInt64` in GameCore next to `SeededRandom`; used by
  `GameViewModel` wheel seed, the hint-reveal seed (currently `String.hashValue` —
  per-launch randomized under a comment claiming reproducibility), and
  `WheelPicker.seed`. Three implementations become one.
- `LevelSelectView` uses `PackCatalog` names: section headers and level names become
  “The Mossward · 3” (capstones marked) instead of “Zen Easy 0”; the in-game HUD title
  follows. The hardcoded section size `10` is replaced by the library's `packSize`.
- Dead code: `UnavailableVisualProvider` deleted (stale “until Image Playground is
  wired in” comment — it is wired in). `GameViewModel.sync()` no longer plays audio as
  a side effect of a function named “sync”; the mood update becomes an explicit call.

## 7. Package fold: four → two

- `LevelKit` (one Codable struct, a dependency it doesn't use, a test that verifies
  the Swift compiler) dissolves: `CutSceneData` moves into GameCore.
- `WordEngine` (only production consumer is a dead `import`) is deleted as a product;
  `InMemoryDictionary` moves into test helpers for whichever test targets stub
  `WordValidating`. The dead import in `GameViewModel` goes.
- `Package.swift`, `project.yml`, imports, README layout diagram all updated.
  The store branch doesn't touch `Package.swift`, so conflict risk is low.

  two packages + app target, runtime deterministic procgen with FM/Image Playground
  enrichment and fallbacks, JSON save in Application Support) — replacing the
  SpriteKit / eight-package / DAWG / SwiftData proposal that was never built.
- `docs/SPEC.md`: “Status: Specification (no code yet)” corrected; Doom Mode section

## 9. Tests where the bugs live

- New unit-test target `ZenWordOfDoomTests` in `project.yml` (the app layer currently
  has **zero** tests across 36 files, and the one confirmed bug lived there):
  - `GameStore`: progress/bestiary/streak mutations, save/load round-trip in a temp
    directory, serenity add/spend guards.
  - `GameViewModel`: completion flow, doom expiry → void → continue, hint seeding
    determinism — against stub `LevelService`/`SoundEngine`/validators.
- New/updated package tests: stir curve (§1), doom void (§3), `fnv1a` stability
  vectors, `DailyPuzzle` determinism (fixed dates → fixed seeds), thrown
  `LevelGenError`s (§5).
- Everything verified per project norms: `swift test` for packages, `xcodebuild` for
  the app target (simulator, fallback providers).

## 10. Economy (spec'd now, implemented after `feat/v0.2-store` merges)

Target numbers (user-approved), balanced against serenity IAP of 10/25/50:

- One reward function in GameCore (natural home: next to `Scoring`; lands cleanly on
  the store branch's GameCore `SaveState`): **+1 serenity per bonus word**, **+5 per
  clear**, **+3 extra for a no-hint clear**; **hint cost 10** (refund rules unchanged).
- Kills the current double-pay (`recordClear` +10/5 *and* `completeLevel` +15/10 —
  25/clear today, i.e. five free hints per level) and the zero payout for words.
- `GameStore` applies the reward exactly once; `GameViewModel` stops adding its own.
- Doom-voided clears (§3) earn no serenity.
- ~2–3 hints earned per pack keeps hints meaningful and IAP relevant but not
  pay-to-win.

**Not implemented on this branch.** A follow-up task runs after the store branch is on
`main`.

## 11. Verification

Per-task: `swift test` (packages) and `xcodebuild build` (app). Before merge:
full `swift test` + `xcodebuild test` (app target incl. the new `ZenWordOfDoomTests`)
+ the review-gate subagent over the whole branch diff. Merge to `main` + push on
green. **No version bump / tag / release without explicit authorization.**
